# What is implemented

The optimizer performs bounded global constant propagation, block-local constant and copy propagation, algebraic simplification, common-subexpression elimination, repeated load reuse, constant-address store forwarding and overwritten-store removal, constant branch simplification, unreachable-block removal, jump threading, unique-predecessor block merging, dead pure-assignment elimination, selected adjacent fused-instruction formation, graph-coloring register reuse, conservative loop-invariant code motion, latency-aware local scheduling, and profile-guided block layout. It can lower an input's `mac` or `addsh` when the selected machine lacks that instruction. The implementation does not include global copy propagation, general alias analysis, or exhaustive dynamic optimization.

The KIR parser, machine reader, and supporting interpreter in `src/kirlib.py` are copied from the COMP10 starter kit's `kirlib.py`. The optimizer passes are original to this project. The interpreter is used by regression tests and by bounded in-memory candidate selection on deterministic synthetic inputs. No sample input files are read by `kopt`.

# Pass order

First parse the program and machine and lower unsupported fused instructions. Then run local value simplification, control-flow cleanup, global constant propagation, further control-flow cleanup, liveness-based dead code removal, loop-invariant motion, a second local simplification and dead-code pass, fused-instruction formation, profile-guided layout, register reuse, and local scheduling. Cleanup before register reuse reduces the graph and opportunities for spills. For small functions, deterministic candidate selection compares a few safe pass combinations and the original input using bounded synthetic execution and the exact machine timing model. The chosen output is serialized deterministically.

# Each pass

Local simplification tracks register versions and constants within each block. It folds operations using KIR's 32-bit rules, reduces multiplication by powers of two to shifts when ALU latency is no greater than multiply latency, forwards copies only while their source is unchanged, and reuses pure expressions only while their inputs and result are unchanged. Repeated loads are reused only after a successful load of the same unchanged address and with no intervening store. A possibly trapping load is never removed without an earlier successful identical load. These operations are expected linear time in instruction count using hash tables.

Memory cleanup tracks stores to proven-valid constant addresses and versions of stored values. A later load of the same address becomes a copy only if the stored value is still available. Unknown-address stores invalidate all stored values. Earlier stores are removed only when overwritten at the same constant address without an intervening load, possible trap, volatile operation, or control-flow boundary. Its expected time is linear in block size.

Global constant propagation uses forward dataflow with an explicit unvisited state and unknown values. Joins retain a constant only when all reachable predecessor states agree; the entry state includes zero-initialized nonparameters and unknown parameters. Loops reach a fixed point before any instruction is rewritten. It is limited to 250 blocks, 4,000 instructions, 256 registers, and one million instruction transfers; exceeding the work bound skips the pass without changing the program. Its cost depends on fixed-point iterations and register count.

Control-flow cleanup folds branches with known conditions, follows jump-only blocks without breaking cycles, removes unreachable blocks, and merges blocks with a unique predecessor. These transformations preserve the sequence of instructions on each reachable path. It runs in expected linear time in instructions and control-flow edges.

Dead code removal computes block liveness with a worklist, then deletes only unused pure instructions. A single block with no outgoing edges is handled with a linear backward scan, including large programs. Other dataflow is bounded to 2,000 blocks and 30,000 instructions and at most 100,000 worklist iterations and two million propagated live-set entries; if the bound is exceeded the pass is skipped. Its worst-case cost depends on graph iterations and live-set size, not just instruction count.

Loop-invariant motion identifies natural loops using dominators and only handles a loop with one unconditional preheader and no side entry. Pure nontrapping expressions whose inputs are never written in the loop, or come from already-hoisted unique definitions that dominate the expression, are computed into a fresh register before the loop; the original destination is still assigned at its original location. This handles zero-trip paths safely and does not move memory operations or traps. Hoisting is limited to four expressions per loop, 250 blocks and 4,000 instructions, and avoids extending code past the instruction-cache limit when the cache penalty is nonzero. Dominator iteration may take quadratic space and multiple graph passes.

Local scheduling runs only when the allocated registers fit in the machine register file and handles regions of at most 48 consecutive pure instructions. It constructs read, write, and anti-dependency edges and chooses a latency-weighted order only if a local issue-width timing estimate improves. Scheduling cannot cross memory operations, traps, volatile operations, or terminators. Its work is quadratic in region length. Profile-guided layout constructs a deterministic trace through the existing blocks, preserving entry and every control-flow edge. It estimates branch and instruction-cache penalties using observed edge counts and changes layout only when this estimated cost falls. It is limited to 250 blocks; the cost estimate and trace selection can take quadratic time.

Fusion replaces adjacent multiplication-plus-add or shift-plus-add when the temporary has only one use in the entire function, the operation is available, and its latency is no greater than the corresponding two-operation latency. Its cost is linear in instructions. Register reuse computes live sets and an interference graph, precolors parameters, and colors the remaining virtual registers deterministically. Initial live values and parameters interfere with one another, preserving zero-initialized registers and arguments. Register reuse is restricted to at most 256 registers, 5,000 instructions, and 500 blocks, and to 50,000 dataflow iterations. Graph construction and coloring can require quadratic space and time in the number of registers, in addition to dataflow work.

# The machine

The machine file is parsed using the starter kit's reader. Fused-instruction availability controls lowering and formation, while fused and unfused latencies constrain formation. Register reuse is enabled only when the number of distinct virtual registers exceeds the available register count and the spill penalty is nonzero. Scheduling uses issue width and instruction latency; profile layout estimates branch and instruction-cache penalties. Memory operations are not reordered, so memory-port utilization is not modeled. For small functions, candidate selection uses the exact simulator timing model, including memory ports, LRU register spills, cache position, and branch fences, on bounded deterministic synthetic traces.

# Keeping the behaviour

Arithmetic uses modulo-2^32 values, signed comparison, division truncated toward zero, and masked shift counts. Division, remainder and memory operations that may trap remain in place unless constant folding proves a nonzero divisor or an earlier identical load has already succeeded. Volatile operations are never deleted or reordered. A store is removed only after proving that a later valid overwrite hides it before any observer or trap. Only pure nontrapping calculations are speculated across branches or loop boundaries; assignments to original destinations remain at their original locations. Register reuse follows control-flow liveness and retains distinct values that can be simultaneously needed.

# Profiles

A supplied profile is used only to estimate layout costs from valid edges that still exist after cleanup. Missing or malformed entries are ignored; without a profile, the pipeline retains the original layout. Candidate selection also considers a version without profile guidance when a profile is supplied. Profiles can be wrong, so layout may be slower on other inputs, but it never changes control-flow semantics.

# Known problems

Some optimizations can increase cycle counts on particular inputs or machines, because static latency and register counts do not capture the simulator's full timing model. Large or complex programs intentionally skip liveness and register reuse to keep runtime bounded. Some cross-block opportunities remain unimplemented; loop motion, scheduling, and profile layout deliberately cover only bounded, conservative cases. Layout and scheduling use approximate costs and may not be profitable on every input. Candidate selection considers at most four optimized pass combinations, one unprofiled candidate when useful, and the original program. The conservative variant disables global propagation as well as hoisting, fusion, and strength reduction. It applies only to functions with at most 1,000 instructions and 100 blocks. Eight deterministic synthetic inputs use at most 4,000 reference steps each; candidate runs use at most 8,000 steps each. Timeouts are skipped for reference runs or reject that candidate. Weighted log cycle ratios emphasize longer traces; ties retain the earlier candidate. Matching outcomes provide an additional guard, not a proof: each transformation must independently preserve semantics. Synthetic inputs may differ from hidden inputs, so candidate selection cannot guarantee the fastest output on every run. Dynamic validation on sampled inputs is not a proof of equivalence. If every possible register name is already used and unsupported fused operations must be lowered, the optimizer reports an error because it cannot allocate a fresh temporary.
